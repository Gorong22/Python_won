## 5. 프로토콜 상대 URL 문제

### 5.1 프로토콜 상대 URL 사용 현황

| 파일               | 위치  | URL 패턴                      | 문제 여부          |
| ------------------ | ----- | ----------------------------- | ------------------ |
| `feed.js`          | 57줄  | `//ecimg.cafe24img.com/...`   | ⚠️ **문제 가능성** |
| `mypage_reader.js` | 6줄   | `//ecimg.cafe24img.com/...`   | ⚠️ **문제 가능성** |
| `index.html`       | 140줄 | `//ecimg.../ex_community/...` | ⚠️ **문제 가능성** |
| `explore.html`     | 다수  | `//ecimg...`                  | ⚠️ **문제 가능성** |
| `community.html`   | 다수  | `//ecimg...`                  | ⚠️ **문제 가능성** |

### 5.2 normalizeImageUrl() 함수 분석

**위치**:

- `feed.js` 12-17줄
- `mypage_reader.js` 16-21줄
- `utils.js` 9-14줄

**함수 내용**:

```javascript
function normalizeImageUrl(url) {
  if (url.startsWith("//")) {
    return window.location.protocol + url;
  }
  return url;
}
```

**문제점**:

1. ✅ 함수는 올바르게 구현됨 (`//` → `https://` 또는 `http://`)
2. ❌ **하지만 실제 사용되지 않는 경우가 많음**:
   - `feed.js` 128줄: `img.dataset.src = fullUrl` (normalizeImageUrl 미사용)
   - `mypage_reader.js` 102, 165줄: 동일
3. ⚠️ `loadImageWithRetry()`에서는 사용되지만, `loadFeedImages()`에서는 사용 안 함

### 5.3 모바일 Safari에서의 문제

**가능한 문제 시나리오**:

1. **프로토콜 상대 URL (`//`)이 모바일 Safari에서 해석 실패**
   - HTTPS 페이지에서 `//ecimg...`는 `https://ecimg...`로 해석되어야 함
   - 하지만 일부 모바일 브라우저에서 실패할 수 있음
2. **data-src에 저장된 URL이 normalizeImageUrl() 없이 사용**
   - `ImageLazyLoader.loadImage()` (utils.js 169줄)에서 `normalizeImageUrl(url)` 사용
   - 하지만 `img.dataset.src`에 이미 `//`로 시작하는 URL이 저장되어 있음

### 6.2 최종 URL을 덮어쓰는 함수 체인

#### Feed 페이지 이미지 로딩 플로우:

```
1. loadFeedImages() [feed.js:74]
   ↓
2. CDN_BASE + fileName [feed.js:128]
   → "//ecimg.../ex_img/a1.webp" (프로토콜 상대 URL)
   ↓
3. img.dataset.src = fullUrl [feed.js:132]
   → data-src에 "//ecimg.../ex_img/a1.webp" 저장
   ↓
4. imageLazyLoader.observe(img) [feed.js:149]
   ↓
5. ImageLazyLoader.loadImage() [utils.js:169]
   ↓
6. const url = img.dataset.src [utils.js:177]
   → "//ecimg.../ex_img/a1.webp" (프로토콜 상대 URL)
   ↓
7. normalizeImageUrl(url) [utils.js:187]
   → "https://ecimg.../ex_img/a1.webp" (정상화됨)
   ↓
8. img.src = normalizedUrl [utils.js:231]
   → ✅ 최종적으로 정상화된 URL 사용
```

**결론**:

- ✅ `ImageLazyLoader`를 통해 로드되는 이미지는 정상화됨
- ❌ **하지만 HTML의 정적 이미지는 정상화되지 않음**

#### HTML 정적 이미지 플로우:

```
1. HTML 파싱
   ↓
2. <img src="//ecimg..."> 직접 로드
   ↓
3. ❌ 프로토콜 상대 URL이 모바일 Safari에서 실패할 수 있음
```

## 7. 종합 분석 및 권장 사항

### 7.1 주요 문제점 요약

1. **프로토콜 상대 URL (`//`) 사용**

   - 모든 CDN URL이 `//ecimg...`로 시작
   - 모바일 Safari에서 해석 실패 가능성

2. **HTML 정적 이미지가 정상화되지 않음**

   - `index.html`, `explore.html`, `community.html`의 정적 이미지
   - JS의 `normalizeImageUrl()`이 적용되지 않음

3. **일관성 없는 URL 처리**

   - `ImageLazyLoader`를 통한 이미지는 정상화됨
   - HTML 정적 이미지는 정상화되지 않음

4. **누락된 JS 파일**
   - `explore.js`, `community.js` 파일이 없음
   - HTML에서 참조하지만 실제 파일 없음

### 7.2 이미지 깨짐 원인 추정

**가장 가능성 높은 원인**:

1. **모바일 Safari에서 프로토콜 상대 URL 해석 실패**

   - HTML의 `<img src="//ecimg...">`가 제대로 로드되지 않음
   - 특히 `explore.html`, `community.html`의 정적 이미지들

2. **CDN_BASE가 프로토콜 상대 URL**

   - JS에서 생성하는 이미지도 `//ecimg...`로 시작
   - `ImageLazyLoader`에서 정상화되지만, 일부 경우 누락 가능

3. **HTML 정적 이미지가 normalizeImageUrl() 적용 안 됨**
   - JS로 동적 생성되는 이미지는 정상화됨
   - HTML에 하드코딩된 이미지는 정상화 안 됨

### 7.3 권장 수정 사항 (참고용, 지금은 수정하지 않음)

1. **CDN_BASE를 절대 URL로 변경**

   ```javascript
   // 현재
   const CDN_BASE = "//ecimg.cafe24img.com/...";

   // 권장
   const CDN_BASE = "https://ecimg.cafe24img.com/...";
   ```

2. **HTML 정적 이미지도 절대 URL로 변경**

   ```html
   <!-- 현재 -->
   <img src="//ecimg.cafe24img.com/..." />

   <!-- 권장 -->
   <img src="https://ecimg.cafe24img.com/..." />
   ```

3. **또는 HTML 로드 시 정적 이미지 정상화**
   ```javascript
   document.querySelectorAll('img[src^="//"]').forEach((img) => {
     img.src = normalizeImageUrl(img.src);
   });
   ```
