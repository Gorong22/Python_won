## 문제 요약

### 발생 현상

- **Safari**: 페이지 로딩 후 즉시 튕김
- **Chrome 모바일**: 일반 모드에서 크래시, 시크릿 모드에서는 정상
- **WebView (카카오톡/네이버 앱)**: 깜빡임 또는 로딩 실패
- **피드/탐색/커뮤니티 페이지**: 이미지가 많이 로드될 때 즉시 크래시
- **검색 결과 표시 시**: 화면이 흰색으로 깜빡이며 종료
- **부분적 이미지 로딩**: 일부는 뜨지만 일부는 로드되지 않음

### 핵심 문제점

1. **이미지 즉시 로딩**으로 인한 GPU 메모리 초과
2. **innerHTML 대량 재렌더링**에 따른 Reflow 폭증
3. **중복된 이벤트 리스너** 등록으로 인한 메모리 누수
4. **DOMContentLoaded 중복 실행**으로 인한 초기화 중복
5. **이미지 디코딩/GC 타이밍 불일치**
6. **WebView 메모리 제한 초과**

## 각 문제의 상세 기술적 원인

### 1. 이미지 즉시 로딩으로 인한 GPU 메모리 초과

#### 발견된 문제점

- **feed.js (74-160줄)**: `loadFeedImages()` 함수가 DOMContentLoaded 시 모든 이미지를 즉시 로드
- **explore.js (101-115줄)**: `renderSearchResults()` 함수가 18개 이미지를 한 번에 `innerHTML +=`로 추가
- **community.js (127-290줄)**: `renderPosts()` 함수가 DocumentFragment를 사용하지만, 이미지 배경을 `style.backgroundImage`로 즉시 설정
- **mypage_reader.js (65-118줄)**: `loadFeedItemImages()` 함수가 모든 feed-item에 이미지를 즉시 로드

#### 기술적 원인

```javascript
// 문제 코드 예시 (explore.js)
function renderSearchResults(keyword = "") {
  searchResults.innerHTML = ""; // 전체 DOM 제거
  for (let i = 0; i < 18; i++) {
    searchResults.innerHTML += `...`; // 18개 이미지를 한 번에 추가
  }
}
```

**문제점:**

- 모바일 GPU는 텍스처 메모리가 제한적 (iPhone 13: 약 1.5GB, iPhone 15: 약 2GB)
- WebP 이미지가 디코딩되면 각각 2-5MB의 GPU 메모리 사용
- 18개 이미지 × 3MB = 약 54MB의 GPU 메모리 즉시 할당
- Safari/WebView는 메모리 제한이 더 엄격 (약 500MB-1GB)

### 2. innerHTML 전체 재렌더링에 따른 대량의 Reflow

#### 발견된 문제점

- **explore.js (102줄)**: `searchResults.innerHTML = ""` 후 18개 항목을 `innerHTML +=`로 추가
- **feed.js (276줄)**: `feedList.innerHTML = ""` 후 `insertAdjacentHTML` 사용 (상대적으로 양호)
- **community.js (130-132줄)**: `while (postList.firstChild)` 루프로 제거 후 DocumentFragment 사용 (양호)

#### 기술적 원인

```javascript
// 문제 코드 (explore.js)
searchResults.innerHTML = ""; // 1. 전체 DOM 제거 → Reflow 발생
for (let i = 0; i < 18; i++) {
  searchResults.innerHTML += `...`; // 2. 각 추가마다 Reflow 발생 (18회)
}
```

**문제점:**

- `innerHTML = ""`는 DOM 트리 전체를 파싱하고 제거 → Reflow 발생
- `innerHTML +=`는 매번 전체 HTML을 재파싱 → 18회 Reflow 발생
- 모바일 브라우저는 Reflow 비용이 PC보다 3-5배 높음
- Safari는 Reflow 중 메인 스레드 블로킹이 심각

### 3. 중복된 이벤트 리스너 등록

#### 발견된 문제점

- **feed.js (443-599줄)**: DOMContentLoaded 내부에서 `querySelectorAll`로 모든 요소에 리스너 추가
- **community.js (309-465줄)**: DOMContentLoaded 내부에서 이벤트 위임 사용하지만, 일부 중복 리스너 존재
- **mypage_reader.js (182-318줄)**: DOMContentLoaded 내부에서 중복 방지 플래그 사용 (양호)

#### 기술적 원인

```javascript
// 문제 코드 (feed.js - 일부)
document.querySelectorAll(".stat-icon-heart").forEach((icon) => {
  if (!icon.hasAttribute("data-listener-attached")) {
    icon.addEventListener("click", ...);  // 정적 요소에만 적용
  }
});
// 하지만 동적으로 생성된 요소에는 적용되지 않음
```

**문제점:**

- 정적 요소와 동적 요소에 대한 이벤트 리스너 관리 불일치
- `querySelectorAll`은 DOMContentLoaded 시점의 요소만 선택
- 동적으로 추가된 요소에는 리스너가 없어 이벤트 위임 필요
- 일부 코드는 이벤트 위임 사용, 일부는 직접 리스너 추가 → 혼재

### 4. DOMContentLoaded 중복 실행

#### 발견된 문제점

- **feed.js (443줄)**: `window.addEventListener("DOMContentLoaded", ...)`
- **community.js (309줄)**: `document.addEventListener("DOMContentLoaded", ...)`
- **explore.js (120줄)**: `document.addEventListener("DOMContentLoaded", ...)`
- **mypage_reader.js (182줄)**: `document.addEventListener("DOMContentLoaded", ...)`

#### 기술적 원인

- 각 JS 파일이 독립적으로 DOMContentLoaded 리스너 등록
- 모든 파일이 defer로 로드되므로 DOMContentLoaded는 한 번만 발생하지만, 각 파일의 리스너가 모두 실행됨
- 이미지 로딩 함수가 여러 파일에서 중복 호출될 가능성

### 5. 이미지 디코딩/GC 타이밍 불일치

#### 발견된 문제점

- **feed.js (136-144줄)**: `img.onload`에서 `this.style.display = "block"` 설정
- **explore.js (131줄)**: `img.src = getRandomExploreImage()` 즉시 설정
- 이미지 로드 실패 시 `img.src = ""`로 메모리 해제 시도하지만, GC 타이밍 불확실

#### 기술적 원인

```javascript
// 문제 코드 (feed.js)
img.onload = function () {
  this.style.display = "block"; // 이미지가 로드되면 표시
};
loadImageWithRetry(img, fullUrl); // 즉시 로드 시작
```

**문제점:**

- 모바일 브라우저는 이미지 디코딩을 백그라운드 스레드에서 수행
- 디코딩 완료 전에 다음 이미지 로드 시작 → 메모리 압박
- GC는 메인 스레드가 idle 상태일 때만 실행
- 연속적인 이미지 로드로 인해 GC 기회 부족

### 6. WebView 메모리 제한 초과

#### 발견된 문제점

- 카카오톡/네이버 앱 WebView는 메인 앱과 메모리를 공유
- WebView 전용 메모리 풀은 약 200-400MB로 제한
- 현재 코드는 50-100개 이미지를 동시에 로드 시도

#### 기술적 원인

- WebView는 네이티브 앱의 메모리 제약을 받음
- Safari/Chrome 독립 앱보다 메모리 제한이 엄격
- 이미지 텍스처가 GPU 메모리를 차지하므로, WebView는 더 빠르게 한계 도달

## 모바일 브라우저 크래시 메커니즘 설명

### iOS WebKit의 메모리 제한 구조

#### 1. 프로세스 메모리 제한

- **iPhone 13**: 약 3GB 프로세스 메모리, WebKit 전용 약 1.5GB
- **iPhone 15**: 약 4GB 프로세스 메모리, WebKit 전용 약 2GB
- **WebView (앱 내)**: 약 200-400MB (앱과 공유)

#### 2. GPU Texture 메모리 한계

- 각 이미지는 디코딩 후 GPU 텍스처로 변환
- WebP 이미지 (1920×1080) ≈ 약 8MB GPU 메모리
- 모바일 GPU는 텍스처 메모리가 제한적 (약 500MB-1GB)
- 메모리 초과 시 브라우저가 프로세스를 강제 종료

#### 3. Safari 렌더링 파이프라인에서의 Reflow 비용

```
PC Chrome: Reflow 1회 ≈ 1-2ms
모바일 Safari: Reflow 1회 ≈ 5-10ms (3-5배 느림)
```

**이유:**

- 모바일 CPU는 단일 코어 성능이 낮음
- Safari는 메인 스레드에서 Reflow 수행 (Chrome은 부분적으로 병렬화)
- `innerHTML +=`는 매번 전체 HTML 재파싱 → 18회 Reflow = 90-180ms 블로킹

#### 4. JS Event Loop 정체

- 이미지 로드 중 `onload` 콜백이 연속 실행
- 각 콜백이 DOM 조작 수행 → Reflow 발생
- 메인 스레드가 블로킹되어 사용자 입력 무응답
- 브라우저가 "응답 없음"으로 판단하여 프로세스 종료

### 크래시 발생 시나리오

#### 시나리오 1: 검색 결과 표시 시 크래시 (explore.js)

```
1. 사용자가 검색창에 입력
2. renderSearchResults() 호출
3. searchResults.innerHTML = "" → Reflow 발생
4. 18개 이미지를 innerHTML +=로 추가 → 18회 Reflow
5. 각 이미지가 즉시 로드 시작 → GPU 메모리 54MB+ 할당
6. GPU 메모리 한계 도달 → Safari가 프로세스 강제 종료
```

#### 시나리오 2: 피드 페이지 스크롤 시 크래시 (feed.js)

```
1. 페이지 로드 시 loadFeedImages() 실행
2. 10개 feed-item-section × 4개 이미지 = 40개 이미지 로드
3. 모든 이미지가 동시에 디코딩 시작
4. GPU 메모리 160MB+ 할당
5. 사용자가 스크롤하여 추가 이미지 노출
6. IntersectionObserver가 추가 이미지 로드 트리거
7. GPU 메모리 한계 초과 → 크래시
```

#### 시나리오 3: WebView에서의 크래시

```
1. 카카오톡/네이버 앱에서 페이지 열기
2. WebView 메모리 풀 (200-400MB) 할당
3. 페이지 로드 시 50개 이미지 로드 시도
4. WebView 메모리 한계 (200MB) 초과
5. 앱이 WebView 프로세스 강제 종료 → 흰 화면
```

## 개선 전략 (단계별)

### 전략 1: 이미지 Lazy Loading 강화 (IntersectionObserver)

#### 목표

- 화면에 보이는 이미지만 로드
- 스크롤 시 점진적으로 로드하여 GPU 메모리 분산

#### 구현 방법

```javascript
// 새로운 이미지 로더 유틸리티 (utils.js에 추가)
class ImageLazyLoader {
  constructor(options = {}) {
    this.options = {
      rootMargin: "50px", // 뷰포트 50px 전에 로드 시작
      threshold: 0.1,
      maxConcurrent: 3, // 동시에 최대 3개만 로드
      ...options,
    };
    this.observer = null;
    this.loadingQueue = [];
    this.loadingCount = 0;
  }

  observe(img) {
    if (!this.observer) {
      this.observer = new IntersectionObserver(
        this.handleIntersect.bind(this),
        {
          rootMargin: this.options.rootMargin,
          threshold: this.options.threshold,
        }
      );
    }
    this.observer.observe(img);
  }

  handleIntersect(entries) {
    entries.forEach((entry) => {
      if (
        entry.isIntersecting &&
        this.loadingCount < this.options.maxConcurrent
      ) {
        const img = entry.target;
        this.loadImage(img);
        this.observer.unobserve(img);
      }
    });
  }

  loadImage(img) {
    if (img.dataset.src && !img.src) {
      this.loadingCount++;
      const url = normalizeImageUrl(img.dataset.src);
      loadImageWithRetry(img, url, 2, 1000);
      img.onload = () => {
        this.loadingCount--;
        this.processQueue();
      };
      img.onerror = () => {
        this.loadingCount--;
        this.processQueue();
      };
    }
  }

  processQueue() {
    // 대기 중인 이미지 처리
  }
}

// 전역 인스턴스
const imageLazyLoader = new ImageLazyLoader();
```

#### 적용 대상

- **explore.js**: `renderSearchResults()` 함수 수정
- **feed.js**: `loadFeedImages()` 함수 수정
- **community.js**: `renderPosts()` 함수 수정
- **mypage_reader.js**: `loadFeedItemImages()` 함수 수정

### 전략 2: innerHTML 제거 및 DocumentFragment 사용

#### 목표

- Reflow 최소화

#### 구현 방법

```javascript
// explore.js 수정
function renderSearchResults(keyword = "") {
  // 기존: searchResults.innerHTML = "";
  // 개선: while 루프로 안전하게 제거
  while (searchResults.firstChild) {
    searchResults.removeChild(searchResults.firstChild);
  }

  const fragment = document.createDocumentFragment();

  for (let i = 0; i < 18; i++) {
    const item = document.createElement("div");
    item.className = "search-item";

    const thumb = document.createElement("div");
    thumb.className = "search-thumb";

    const img = document.createElement("img");
    img.dataset.src = getRandomExploreImage(); // data-src 사용
    img.loading = "lazy";
    img.style.objectFit = "cover";
    img.style.width = "100%";
    img.style.height = "100%";

    thumb.appendChild(img);
    item.appendChild(thumb);

    // ... 나머지 요소 생성

    fragment.appendChild(item);
  }

  searchResults.appendChild(fragment); // 한 번에 추가 → Reflow 1회만
}
```

- **explore.js (102-115줄)**: `renderSearchResults()` 함수

### 전략 4: DOMContentLoaded 중복 리스너 제거

#### 목표

- 초기화 함수를 한 번만 실행
- 각 파일의 초기화 로직을 모듈화

#### 구현 방법

```javascript
// 새로운 초기화 관리자 (app.js에 추가)
class AppInitializer {
  constructor() {
    this.initialized = false;
    this.initCallbacks = [];
  }

  register(callback) {
    if (this.initialized) {
      callback();
    } else {
      this.initCallbacks.push(callback);
    }
  }

  init() {
    if (this.initialized) return;
    this.initialized = true;
    this.initCallbacks.forEach((cb) => cb());
  }
}

const appInit = new AppInitializer();

// DOMContentLoaded는 한 번만 등록
if (document.readyState === "loading") {
  document.addEventListener("DOMContentLoaded", () => appInit.init());
} else {
  appInit.init();
}

// 각 파일에서 사용
// feed.js
appInit.register(() => {
  loadFeedImages();
  // ... 기타 초기화
});

// explore.js
appInit.register(() => {
  // ... 초기화
});
```

#### 적용 대상

- **모든 JS 파일**: DOMContentLoaded 리스너를 appInit.register()로 변경

### 전략 5: 스크롤 핸들러 최적화 (Throttle/Debounce)

#### 목표

- 스크롤 이벤트 빈도 감소
- 메인 스레드 블로킹 최소화

#### 구현 방법

```javascript
// utils.js에 추가
function throttle(func, limit) {
  let inThrottle;
  return function () {
    const args = arguments;
    const context = this;
    if (!inThrottle) {
      func.apply(context, args);
      inThrottle = true;
      setTimeout(() => (inThrottle = false), limit);
    }
  };
}

// 사용 예시

// 메모리 모니터링 유틸리티
class MemoryMonitor {
  constructor() {
    this.maxImages = 20; // 동시에 최대 20개 이미지만 로드
    this.loadedImages = new Set();
  }

  canLoadMore() {
    return this.loadedImages.size < this.maxImages;
  }

  registerImage(img) {
    if (this.loadedImages.size >= this.maxImages) {
      // 가장 오래된 이미지 제거
      const oldest = Array.from(this.loadedImages)[0];
      this.unregisterImage(oldest);
    }
    this.loadedImages.add(img);
  }

  unregisterImage(img) {
    img.src = "";
    img.onload = null;
    img.onerror = null;
    this.loadedImages.delete(img);
  }
}

const memoryMonitor = new MemoryMonitor();

// 이미지 로드 시 사용
function loadImageSafely(img, url) {
  if (!memoryMonitor.canLoadMore()) {
    console.warn("Memory limit reached, skipping image load");
    return;
  }

  memoryMonitor.registerImage(img);
  loadImageWithRetry(img, url);

  img.onload = () => {
    // 로드 완료 후 처리
  };
}
```

#### 적용 대상

- **모든 이미지 로딩 함수**: MemoryMonitor 통합

4. **이벤트 위임 통일**로 메모리 누수 방지

이러한 개선을 통해 모바일 브라우저에서도 안정적으로 동작하는 웹 애플리케이션을 구현할 수 있습니다.
